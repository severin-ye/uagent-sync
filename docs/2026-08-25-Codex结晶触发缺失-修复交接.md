# Codex 中“结晶”触发缺失：修复交接

- 交接日期：2026-08-25
- 目标项目：`C:\Users\6seve\Codelib-severin\2_Business\uagent-sync`
- 当前结论：结晶的底层执行能力仍然存在，但当前发布给 Codex 的 Skill 集合缺少结晶入口，因此新会话无法把用户只说的“结晶”识别成 uagent-sync 操作。
- 本文状态：待新会话实施；本文只负责交接，不代表修复已经完成。

## 1. 用户原本期待的行为

用户已经安装并加载 uagent-sync 后，在 Codex 中只说“结晶”或“结晶这个安装”，Codex 就应理解为调用 uagent-sync 的 crystallize 工作流，而不是把“结晶”当成普通中文词语。

该工作流的既有语义是把刚完成的环境变更固化为可迁移、可追溯的状态，现有实现将其组织为四步：

1. 写入安装来源记录。
2. 生成 `SYNC-GUIDE.md` 和相关说明。
3. 导出工作区状态 JSON。
4. 执行 Git 暂存、提交和推送。

新修复的首要目标是恢复自然语言触发，不是重新设计 crystallize 的业务逻辑。

## 2. 当前实际现象

重启 Codex 后，uagent-sync 的以下三个 Skill 可以被发现：

- `uagent-sync-update`
- `uagent-sync-backup`
- `uagent-sync-restore`

但是 `skills/` 中没有 `uagent-sync-crystallize`，所以“结晶”不会命中任何已发布 Skill 的名称或 description，Codex 只能按照普通语义理解它。

这说明问题发生在“Codex 如何发现并触发功能”这一层，不足以说明 crystallize 执行代码被删除或失效。

## 3. 已核对的源码证据

### 3.1 Codex 的插件清单会扫描 `skills/`

`.codex-plugin/plugin.json` 中存在：

```json
"skills": "./skills/"
```

因此 Codex 插件发布面实际以仓库的 `skills/` 目录为入口。

### 3.2 当前 `skills/` 只有三个公开入口

当前目录内容为：

```text
skills/
├─ uagent-sync-backup/
├─ uagent-sync-restore/
└─ uagent-sync-update/
```

没有用于承接“结晶”的第四个 Skill。

### 3.3 OpenCode 工具仍保留自然语言触发说明

`src/plugin.ts` 中仍注册 `opencode_sync_crystallize`，其描述明确写有：

```text
Trigger with natural language: "crystallize this install" / "结晶这个安装"
```

这证明旧语义仍保留在 OpenCode 工具适配层。

### 3.4 CLI 仍保留 crystallize 命令

`src/cli.ts` 中仍存在 `case "crystallize"`，并依次生成安装记录、指南、状态文件和 Git 固化结果。

### 3.5 DSH 适配层仍保留 crystallize 工具

`packages/dsh/index.js` 中仍注册 `sync_crystallize`，描述同样保留“结晶这个安装”的自然语言触发说明。

## 4. 根因判断

当前是一个“执行能力存在、Codex 可发现入口缺失”的适配与打包问题：

```text
用户说“结晶”
    ↓
Codex 只从已发布 Skill 的 name / description 判断是否调用
    ↓
当前只有 update / backup / restore
    ↓
没有 crystallize Skill 可以命中
    ↓
“结晶”被当成普通词语
```

`AGENTS.md`、OpenCode tool description 或 DSH tool description 即使写有“结晶”，也不会自动变成所有 Codex 项目中的全局 Skill 触发器；Codex 需要在插件实际发布的 `skills/` 中看到对应 Skill。

## 5. 建议修复范围

### 5.1 必须完成

新增一个叶子 Skill：

```text
skills/uagent-sync-crystallize/
├─ SKILL.md
└─ agents/openai.yaml
```

其 `SKILL.md` 至少需要做到：

- `name` 与目录名一致，使用 `uagent-sync-crystallize`。
- description 明确包含中文触发词“结晶”“结晶这个安装”和英文 `crystallize this install`。
- 明确它调用现有 uagent-sync CLI，而不是复制一套新的 crystallize 实现。
- 明确 `type`、`name`、`source` 等 CLI 必填输入如何从当前安装上下文取得。
- 当前上下文不足时，只追问无法安全推断的必填信息。
- 明确写出提交与推送属于该命令的既有外部副作用，不能把 dry-run 或普通导出冒充已经结晶。
- 保留现有 `--skip-push` 等能力，但不得未经核对改变默认语义。

`agents/openai.yaml` 应沿用现有三个 Skill 的项目格式，给出清晰的显示名称、简短说明和默认提示，使 Skill 在 Codex 中容易辨认。

### 5.2 原则上不需要改动

- 不需要重写 `src/cli.ts` 中已经存在的 crystallize 实现。
- 不需要把 OpenCode、DSH 和 Codex 合并成同一种运行时。
- `.codex-plugin/plugin.json` 已经指向整个 `skills/`，若现有打包测试确认自动收集子目录，通常无需增加逐项清单。
- 不要直接修改 `C:\Users\6seve\.codex\plugins\cache\...` 中的安装缓存；缓存是安装产物，不是源码事实源。

### 5.3 只有发现真实缺陷时才扩大范围

如果新增 Skill 后发现 CLI 参数、提交行为或 Windows 路径确实有错误，可以另行修复，但必须：

1. 先用 GitNexus 对将修改的函数或方法运行 impact analysis。
2. 先增加能够复现缺陷的失败测试。
3. 把“恢复触发入口”和“修复底层行为”分成清楚的变更说明。
