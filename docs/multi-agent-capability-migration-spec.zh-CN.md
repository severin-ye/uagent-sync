# 多 Agent 能力迁移工作台设计说明

状态：主设计文档  
最后更新：2026-08-14  
适用项目：`uagent-sync`  
覆盖平台：Codex、OpenCode、DeepSeek Harness

> 本文是后续产品讨论和实现的单一编辑入口。今后优先对本文做增量修改，不再依赖聊天中反复生成整份说明。

## 1. 文档结论

`uagent-sync` 不应只做配置文件复制，而应升级为一个双向的 Agent 能力迁移工作台：

1. 识别来源平台实际具备的能力及其实现载体；
2. 检查目标平台是否已有原生能力；
3. 追溯原扩展的官方仓库，优先采用同一项目提供的目标平台版本和官方安装方法；
4. 原项目未适配时，寻找成熟且能力边界接近的替代方案；
5. 对已经证实兼容的 Skill、MCP Server、CLI 或脚本提供迁移预览；
6. 只有前述路径全部不可用时，才把桥接或自行开发作为低优先级兜底选项；
7. 任何下载、安装和配置修改都必须由用户明确确认。

迁移单位是“能力”，不是插件名称，也不是某个配置字段。

系统默认采用“保留优先”策略：确认存在目标平台官方版本的来源扩展，应默认纳入迁移计划。目标平台已有重复原生能力，不构成自动跳过迁移的理由；它会触发一项独立的启用冲突决策。用户可以迁入后继续使用原扩展、改用目标原生能力，或保留两者。

## 2. 对早期说法的修正

### 2.1 Codex 与 OpenCode 不能笼统视为同一个插件生态

Codex 与 OpenCode 之间之所以可能迁移得比较顺，通常是因为用户资产中存在大量通用层：

- 项目文件和 Git 仓库；
- `AGENTS.md` 等指令文件；
- `SKILL.md`；
- Shell、CLI 和普通脚本；
- MCP Server；
- Markdown 工作流和提示词。

这不代表 Codex Extension 与 OpenCode Plugin 使用同一套接口。两者的清单格式、注册接口、生命周期、权限模型和安装方式仍应分别建模。迁移顺畅的证据来自公共资产，而不是“插件天然兼容”。

### 2.2 DeepSeek Harness 的插件只是同类概念，不是同一格式

DeepSeek Harness 的 Cordis Plugin/Profile Bundle、OpenCode Plugin、Codex Extension 都可以扩展 Agent，但不能当成可互换的软件包。

系统必须保留三种独立载体：

```text
codex_extension
opencode_plugin
deepseek_cordis_plugin
```

“插件”只能作为产品界面的上位分类，不能作为迁移兼容性的证据。

### 2.3 MCP 要拆成 Server 资产和 Client 接入能力

以下两句话不能混为一谈：

- MCP Server 使用标准协议，因此其代码、工具定义和后端数据源通常具有跨客户端复用潜力；
- 目标 Agent 是否具备可用的 MCP Client、支持何种传输和认证方式，必须按目标版本单独验证。

因此，正确结论是：

```text
MCP Server 可复用潜力：较高
MCP 配置文件可直接复制：不能默认成立
目标平台可实际接入：需要版本和本机证据
```

截至本文日期，本机安装的 DeepSeek Harness 为 `@deepseek-ai/dsh 0.1.0-rc.6`，配置根目录为 `~/.dsh`。当前项目只确认了该安装及其 Web Profile Bundle，没有取得足够证据证明它已经提供通用 MCP Client。因此看板必须继续显示“待验证”，不能显示“直接共享”。这是一条本机、版本化结论，不是对未来版本的永久判断。

### 2.4 GitHub Topic 数量不等于可安装插件数量

`dsh-plugin` Topic 或任何社区目录只能用于发现候选项目。仓库数量不能直接代表：

- 真正使用 DSH 插件接口；
- 可以安装；
- 与当前 DSH 版本兼容；
- 仍在维护；
- 安全可信；
- 能力边界完整。

类似“已有约 299 个插件”或“某插件已经成熟”的结论不得写入稳定产品规则。动态生态数据必须带来源、检查时间和审核状态。

### 2.5 “直接共享”不能由类型名称自动推导

早期实现把来源平台的 MCP 标成 `portable`，进而生成“直接共享”建议。这是不准确的。

“可直接迁移”必须同时具备：

- 目标平台明确支持该载体；
- 原项目或协议文档明确支持目标平台；
- 版本范围已知；
- 配置字段、启动方式和认证方式已核对；
- 不复制密钥值和本机私有状态；
- 有安装后验证方法和撤销方法。

缺少任何关键证据时，应降级为“待验证”“需要重新配置”或“推荐替代方案”。

## 3. 产品目标与非目标

### 3.1 产品目标

- 支持三个平台之间全部六条迁移方向；
- 识别公共能力、平台原生能力和扩展提供的能力；
- 发现同一扩展项目的官方跨平台版本；
- 找到并比较成熟替代方案；
- 给出推荐、原因、证据和能力差异；
- 在用户确认后执行安装、配置、验证和回滚；
- Web、CLI 和 Agent 对话共用同一决策引擎。

### 3.2 非目标

- 不把三套插件接口强行统一成一种格式；
- 不保证每项能力都能无损迁移；
- 不自动迁移 Session、Memory、聊天历史、主题和 UI 状态；
- 不复制 API Key、Token、OAuth 凭据或环境变量值；
- 不因搜索到 GitHub 仓库就自动安装；
- 不默认推荐自行开发适配器。

## 4. 六条双向迁移路线

```text
Codex    → OpenCode
Codex    → DeepSeek Harness
OpenCode → Codex
OpenCode → DeepSeek Harness
DeepSeek Harness → Codex
DeepSeek Harness → OpenCode
```

用户必须显式选择来源和目标。系统不能固定以 DeepSeek 为唯一目标，也不能用一个平台的推荐结果反推另一方向。

同一能力在相反方向上可能得到不同结论。例如：

- Codex → OpenCode：Codex 原生 Word 能力可能需要寻找 OpenCode 扩展；
- OpenCode → Codex：OpenCode 的 Word MCP 可能被 Codex 原生能力完整替代，不需要安装 MCP。

## 5. 核心数据模型

### 5.1 能力 `Capability`

能力描述用户实际能完成的工作，例如：

- 读取 Word 正文；
- 提取 Word 表格；
- 修改 Word 并保留格式；
- 搜索代码；
- 操作 GitHub；
- 读取 Notion；
- 浏览网页；
- 调用子 Agent。

能力必须允许拆成更细的能力边界。不能只记录“支持 Word”，因为读取、结构解析、批注、修改和导出是不同能力。

### 5.2 实现载体 `CapabilityProvider`

一项能力可以由以下载体提供：

- 目标平台原生能力；
- Codex Extension；
- OpenCode Plugin；
- DeepSeek Cordis Plugin/Profile Bundle；
- MCP Server；
- Skill；
- CLI；
- Script；
- Hook；
- 自定义 Tool；
- 桥接器或适配层。

### 5.3 扩展身份 `ExtensionIdentity`

用于判断两个不同安装包是否属于同一项目：

- 官方仓库 URL；
- 项目主页；
- 维护者或组织；
- 包名和平台专用包名；
- manifest 中的 repository 信息；
- README 中的官方安装说明；
- 发布签名和版本关系。

仅名称相似不能证明是同一扩展。

### 5.4 平台实现 `PlatformImplementation`

同一扩展可以为不同平台提供完全不同的实现：

```text
项目：Superpowers
├── Codex 安装方法
├── OpenCode 安装方法
└── 其他平台安装方法
```

系统应采用目标平台的官方安装说明，而不是复制来源平台目录。

### 5.5 证据 `Evidence`

每条事实和建议至少包含：

- 来源类型；
- 来源 URL 或本机路径；
- 检查时间；
- 适用版本；
- 证据摘要；
- 可信等级。

建议的证据等级：

| 等级 | 含义 |
|---|---|
| `local_verified` | 已在当前机器和版本上验证 |
| `official_documented` | 官方仓库或文档明确说明 |
| `official_inferred` | 根据官方代码结构推断，尚未运行验证 |
| `community_reported` | 社区项目或说明声称支持 |
| `unverified` | 仅发现候选，尚未核验 |

### 5.6 迁移副本 `ManagedMigrationItem`

迁移系统必须记录自己带入目标平台的每一项资产，不能只记录最终配置结果。至少包括：

- 来源平台、目标平台和原始扩展身份；
- 目标平台安装包、版本和安装来源；
- 用户选择的迁移方案和推荐理由；
- 创建或修改的文件；
- 当前状态：已安装并启用、已安装但停用、未安装、已卸载；
- 能力冲突和运行时优先级；
- 验证结果；
- 回滚和删除方法。

这份记录使系统可以安全完成“统一停用所有迁入插件”“只停用冲突项”“重新启用”“统一卸载”或“逐项删除”，而不是依靠再次猜测文件归属。

### 5.7 三个彼此独立的决策维度

每个迁移项必须分别回答三个问题：

1. **是否迁入**：是否下载或复制目标平台实现；
2. **是否启用**：迁入后是否进入目标 Agent 的活动配置；
3. **冲突时使用谁**：来源扩展的目标版本、目标平台原生能力，或两者并存。

不能因为系统推荐目标原生能力，就自动把“是否迁入”改成否；也不能因为插件已经迁入，就自动启用并覆盖目标原生行为。

## 6. 迁移决策顺序

对每项来源能力，系统应先做候选调查，再让用户决定迁入和启用策略。第 1 和第 2 项都属于最高优先层，需要根据能力覆盖和用户连续性并列比较。

### 6.0 默认迁入基线

如果系统已经确认某个来源扩展存在由同一项目提供、兼容目标平台的官方版本，则该版本默认进入迁移计划。这里的“同一扩展”必须由仓库、维护者、manifest 或官方文档确认，不能只凭同名判断。

默认进入计划不等于静默安装。系统仍需展示将安装什么，并在写入前取得用户确认。

如果目标平台已有功能重复的原生能力或其他扩展，系统不得擅自丢弃来源扩展，而应生成冲突选择：

- 迁入并启用来源扩展的目标平台版本；
- 迁入但先停用，运行时使用目标原生能力；
- 两者都保留并启用；
- 不迁入；
- 暂不决定。

系统可以推荐其中一种，但推荐不能替代用户选择。

### 6.1 目标平台原生能力

检查目标平台是否已经完整或部分提供该能力。原生能力覆盖完整时，系统通常应推荐优先使用原生能力，但不能据此自动取消来源扩展的迁入计划。

系统必须说明：

- 覆盖了哪些子能力；
- 缺少哪些子能力；
- 为什么优先原生；
- 来源平台的配置或工作流是否仍需迁移；
- 两者并存是否会产生工具重名、重复触发、权限扩大或行为不一致。

### 6.2 原扩展的官方目标平台版本

找到原扩展的官方仓库，检查 README、平台目录、发布记录和安装文档。

如果同一项目已经提供目标平台实现，应默认纳入迁移计划并采用其官方安装方法。不同平台的包、目录或接口可以完全不同；只要扩展身份和官方支持关系明确，就应视为“官方跨平台安装”，而不是“自行转换”。

即使目标平台已有功能重复的原生能力，也要保留这个官方版本作为用户可选项。系统需要同时解释“保持原工作流连续性”和“使用目标原生能力”的利弊。

### 6.3 成熟替代扩展

原项目未适配目标平台时，再寻找能力边界相近的成熟替代品。默认展示两到三个候选，不直接替用户安装。

候选排序至少考虑：

- 子能力覆盖率；
- 官方或社区维护身份；
- 最近发布和提交状态；
- 文档和测试完整度；
- 安全与权限范围；
- Windows 兼容性；
- 安装和配置成本；
- API Key 或外部服务依赖；
- 离线能力；
- 与目标 Agent 的集成深度。

### 6.4 已验证的通用载体迁移

对于 Skill、MCP Server、CLI 和脚本，检查目标平台支持及实际配置差异。只有证据完整时才显示“可直接迁移”。

即使直接迁移，也必须解释：

- 为什么兼容；
- 会复制、引用或生成哪些文件；
- 目标配置放在哪里；
- 需要哪些依赖和密钥名称；
- 哪些本机状态不会迁移；
- 如何验证和撤销。

### 6.5 成熟桥接器

接口不同但存在成熟桥接项目时，可以作为普通候选。必须明确新增依赖、常驻进程、权限、安全边界和版本耦合。

### 6.6 自行转换或开发适配

这是最后兜底，不是默认推荐。

在 Agent 对话、CLI 和 Web 中均应遵守：

- 不默认选中；
- 不使用“推荐”徽标；
- 不放在首要主按钮；
- 与“不迁移”同时出现；
- 展示开发成本、维护成本、能力缺口和版本风险；
- 只有用户明确选择后才生成或修改代码。

### 6.7 不迁移

“不迁移”是正式决策，不是错误。系统应记录原因并允许用户以后重新评估。

## 7. 推荐结果类型

旧的 `portable / adaptable / native_only` 更适合描述资产属性，不足以直接表示迁移决策。面向用户的建议应改为：

| 建议类型 | 含义 |
|---|---|
| `use_target_native` | 使用目标平台已有原生能力 |
| `install_official_variant` | 安装同一项目的官方目标平台版本 |
| `install_alternative` | 安装经过比较的成熟替代品 |
| `migrate_verified` | 已有证据支持直接迁移通用载体 |
| `reconfigure` | 底层能力可复用，但需按目标格式重新配置 |
| `use_bridge` | 使用成熟桥接器 |
| `needs_verification` | 证据不足，暂不能执行 |
| `custom_fallback` | 自行转换或开发，仅作兜底 |
| `skip` | 不迁移或暂不处理 |

每条建议都必须包含推荐原因；“可直接迁移”也不能省略解释。

建议类型描述“系统认为哪种实现更合适”，不直接决定安装状态。每条建议还应附带独立的执行选择：

| 执行选择 | 含义 |
|---|---|
| `install_enable` | 迁入并启用 |
| `install_disable` | 迁入但暂不启用 |
| `keep_both` | 原扩展目标版本与目标原生/现有扩展都启用 |
| `do_not_install` | 本次不迁入 |
| `defer` | 暂不决定 |

当两套实现同时启用时，系统还要记录具体路由或优先级；如果目标平台无法可靠控制优先级，应警告用户，而不是假装“两个都保留”一定无冲突。

## 8. 示例：Codex → OpenCode 的 Word 能力

### 8.1 来源识别

```text
能力族：Word 文档处理
来源实现：Codex 原生扩展
子能力：正文读取、结构识别、表格提取、批注、修改、导出
```

### 8.2 目标调查

系统依次完成：

1. 检查 OpenCode 是否有等价原生能力；
2. 查找该 Codex 扩展的官方仓库，检查是否提供 OpenCode 版本；
3. 若无官方适配，搜索成熟的 OpenCode Plugin、MCP、Skill 或 CLI；
4. 按子能力覆盖、维护状态、安全性和安装成本排序；
5. 把候选结果可视化返回用户。

### 8.3 用户看到的结果

```text
来源能力：Word 文档处理
目标现状：OpenCode 未检测到完整原生覆盖

候选 A：原项目官方 OpenCode 版本
证据：官方 README
能力覆盖：5/6
配置方式：使用官方 OpenCode 安装流程
推荐原因：同一项目维护，行为一致性最高

候选 B：成熟 Word MCP
证据：仓库、发布和本机验证待列出
能力覆盖：4/6
代价：需要本地运行时和目标 MCP Client

候选 C：暂不迁移
影响：继续在 Codex 中处理 Word
```

“自行开发 OpenCode 插件”只在展开“更多选择”后出现，并明确标记为兜底。

### 8.4 示例：OpenCode → Codex 的重复能力冲突

假设 OpenCode 中安装了一个扩展，系统确认同一项目提供 Codex 官方版本，同时 Codex 自身已经原生具备大部分相同能力。

系统的默认迁移草案应是：

```text
迁入：是（采用该项目官方 Codex 安装方式）
启用：等待用户规则
冲突：Codex 原生能力与迁入扩展部分重复
推荐：优先使用 Codex 原生能力，但保留迁入扩展以维持原工作流
```

用户可以对全部重复项应用一次规则：

```text
A. 全部迁入并启用来源扩展
B. 全部迁入，但冲突项停用，使用 Codex 原生能力
C. 两者都启用
D. 每项分别询问
E. 本次不迁入重复项
```

随后用户仍可逐项覆盖。例如 Word 能力选择 Codex 原生，某个具有独特工作流的代码审查扩展选择迁入并启用。最终迁移计划必须同时展示全局规则和例外项。

这套处理可直接推广到另外五个方向。区别只在于各平台对“停用”“并存”“工具优先级”和“官方目标版本”的实现方式不同，公共决策模型保持一致，平台 adapter 负责落实具体配置。

## 9. Web 看板交互

### 9.1 迁移方向

```text
从：[Codex ▼]  到：[OpenCode ▼]
```

来源与目标相同应禁用迁移分析。

### 9.2 能力卡片

每张卡片显示：

- 能力及子能力；
- 来源实现和载体；
- 目标平台现状；
- 首选方案及候选方案；
- 推荐原因；
- 能力覆盖差异；
- 证据等级和最后检查时间；
- 安装复杂度、权限和风险；
- 当前批量规则和本项覆盖规则；
- 迁入状态、启用状态和冲突时的实际使用方；
- `查看依据`、`比较候选`、`预览安装`、`暂不处理`。

### 9.3 批量规则与逐项覆盖

用户可以先选择一条规则处理全部项目，再对任意项目单独修改。建议提供的全局规则包括：

- 所有已确认的官方目标平台版本都迁入并启用；
- 所有官方版本都迁入，但与目标原生能力冲突的项目先停用；
- 冲突时统一优先使用目标原生能力；
- 冲突时统一优先保持来源扩展工作流；
- 冲突时两者都保留；
- 每一项都询问。

规则优先级为：

```text
单项选择 > 能力类别规则 > 本次迁移全局规则 > 系统默认值
```

应用全局规则后，界面必须显示受影响项目数、例外项目数和冲突项目数。用户逐项修改后，系统不能因为再次切换页面或重新扫描而覆盖这些选择。

对于每个冲突项，系统至少提供以下上下文：

- 两种实现各自覆盖的子能力；
- 推荐选项和理由；
- 保留原扩展对工作流连续性的价值；
- 使用目标原生能力对稳定性、权限和维护的价值；
- 两者共存的工具命名、路由、重复调用和权限风险；
- 停用与卸载的区别；
- 将来批量停用或删除时会发生什么。

### 9.4 停用、卸载与删除

- **停用**：保留安装文件和迁移记录，从活动配置中关闭；
- **卸载**：执行目标扩展的标准卸载流程，但保留迁移历史；
- **删除记录**：仅在用户明确要求时移除迁移历史；不应与卸载自动绑定。

系统必须支持对所有迁入项、所有冲突项、某一能力类别或单个项目执行停用和卸载。批量操作前仍需显示差异并确认。

### 9.5 写操作

扫描、比较和候选搜索均为只读。只有用户打开安装预览并再次确认，系统才可以执行写操作。

安装预览必须显示：

- 下载来源和固定版本；
- 将创建、修改或删除的文件；
- 配置差异；
- 所需密钥名称，但不读取或复制密钥值；
- 是否需要重启；
- 验证步骤；
- 回滚步骤。

## 10. CLI 与 Agent 对话

三种入口共用同一迁移引擎。

建议 CLI：

```text
uagent-sync migrate plan --from codex --to opencode
uagent-sync migrate inspect <capability-id>
uagent-sync migrate candidates <capability-id>
uagent-sync migrate policy set <policy-id>
uagent-sync migrate choose <item-id> --action <action>
uagent-sync migrate preview <candidate-id>
uagent-sync migrate apply <candidate-id>
uagent-sync migrate disable --scope migrated|conflicts|category|item
uagent-sync migrate uninstall --scope migrated|conflicts|category|item
uagent-sync migrate verify <migration-id>
uagent-sync migrate rollback <migration-id>
```

`apply` 必须基于已生成的 preview，并要求明确确认。

Agent 对话应先返回调查结果和选项，不应直接下载或修改配置，也不应主动把自研适配描述为推荐路线。对话、CLI 和 WebUI 必须读取和修改同一份迁移草案与用户选择，保证用户可以在一个入口设置全局规则，再到另一个入口逐项调整。

## 11. 安全边界

默认不得迁移：

- API Key、Token 和 OAuth 凭据；
- Session、Memory 和聊天历史；
- 用户权限和审批状态；
- 本机缓存；
- 主题、快捷键和 UI 状态；
- 含密钥的 URL；
- 未经确认的环境变量值。

允许记录密钥需求名称，例如 `NOTION_TOKEN`，但值必须显示为未读取、未复制。

所有写操作遵循：

```text
备份 → 展示差异 → 用户确认 → 执行 → 验证 → 支持回滚
```

## 12. 动态生态调查规则

扩展推荐涉及实时 GitHub、官方文档和发布信息，必须在线核验。推荐记录至少保存：

- 官方仓库或主页；
- 平台支持原文所在位置；
- 最新稳定版本和发布日期；
- 最近维护时间；
- 安装说明；
- 权限和密钥需求；
- 测试或验证证据；
- 本次检查时间。

GitHub stars、Topic 归类和搜索排名只能作为发现信号，不能单独证明成熟度或兼容性。

## 13. 分阶段实施

### 阶段 A：修正迁移模型

- 将迁移 API 从固定 `target=deepseek` 改为显式 `from` 与 `to`；
- 拆分能力、载体、扩展身份、平台实现和证据；
- 停止由 `portable` 自动生成“直接共享”；
- 为当前看板中的不确定建议改成“待验证”；
- 分离“推荐方案”“是否迁入”“是否启用”和“冲突路由”；
- 建立迁入项来源记录，为统一停用、卸载和回滚提供依据。

### 阶段 B：六向本机比较

- 支持全部六条迁移路径；
- 识别目标原生能力；
- 展示能力缺口而不是仅比较名称；
- 支持全局规则、类别规则和逐项覆盖；
- 保留只读和密钥脱敏。

### 阶段 C：官方扩展身份解析

- 解析 manifest、repository、包名和 README；
- 识别同一项目的不同平台实现；
- 返回官方平台安装方法和版本证据。

### 阶段 D：成熟替代品调查

- 在线搜索候选；
- 按能力覆盖、维护、安全和成本排序；
- 保存带日期的证据快照；
- 让用户比较并选择。

### 阶段 E：确认式安装

- 安装预览；
- 配置备份和差异；
- 用户确认；
- 安装、重启提示、能力验证和回滚。

### 阶段 F：平台原生适配

- 仅在没有成熟方案且用户主动选择时提供自研适配；
- Cordis、OpenCode、Codex 专用代码保持在独立 adapter 中；
- 版本变化不得污染公共迁移核心。

## 14. 当前实现与本文的差距

当前 Web 看板已经完成三平台只读扫描和基础展示，但迁移建议仍有以下欠缺：

- 固定以 DeepSeek 为目标；
- 主要按能力载体名称比较，尚未建立细粒度能力边界；
- 没有追溯官方仓库和平台专用安装说明；
- 没有成熟替代品搜索与排名；
- `portable` 仍可能被解释为“直接共享”；
- 没有安装预览、确认、验证和回滚流程。

因此，当前页面应理解为“初步配置缺口清单”，不能理解为已经验证可执行的迁移方案。
